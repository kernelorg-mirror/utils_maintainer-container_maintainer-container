              Optional protocols
              
  
              The archives are already served over HTTP. Turn on IMAP or
  NNTP to reach the same mail from a mail client or a newsreader instead.
  Both are served by the process that already serves the web port, so
  turning one on costs nothing while it sits idle. (An MCP endpoint, for
  putting the archive in reach of an AI assistant, is planned but not built
  yet.)

    as well, so an agent can search it itself rather than be told what is
    in it. It is a plain HTTP server -- streamable HTTP transport, no

                  That address is the whole of it. Any MCP client will
    take it, whether it is driving a model on this machine or one
    somewhere else; the server neither knows nor cares which.

                  Spellings differ -- some clients want
    "streamable-http" or "streamableHttp" in

    rather than under mcpServers, and
    "maintainer-container" is just the handle the tools

                  A client that speaks only stdio needs a bridge in
    front of it, which is a one-liner rather than a reason to give
    up:
                  
    
                  
    
                  The server answers in records -- who wrote what,
    when, in which thread -- and never in message bodies. For the text of
    a message it sends the agent to b4 mbox, which is why
    the b4 setting above is worth doing first. That also keeps what
    reaches a model small, which matters more on a local one.
                  
    
                  There is no authentication, by design: what protects
    this is the address. Keep the published port on
    127.0.0.1, and reach it from another machine over an SSH
    forward rather than by binding it to a public interface.

                  The configs worth editing by hand live on the
    /data volume. Each one is watched: save a change and the
    service that reads it picks it up within a few seconds, with no restart
    from you.
